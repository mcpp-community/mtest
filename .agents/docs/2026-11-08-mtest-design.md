# mtest：面向 Agent 时代的通用测试系统

**日期：** 2026-11-08
**状态：** 第二版，M1–M5 已决定；0.1.0（PR #1）实现协议 v1、C++ 库、引擎与服务、适配与一致性套件；0.2.0 实现 mcpp 顶层方案 W8 的 mtest 部分：`[discover.<name>]` 组、`[cases]` 与宿主清单中的用例属性、`--shard`、覆盖映射（`docs/coverage.md`）、静态用例清单（`mcpplibs.mtest.manifest`、`mtest list --static`）。构建插件形式的静态清单不采用：mcpp 以 `[package.metadata.mtest]` 保存工具的表，引擎直接读取清单与测试源，无须每次构建运行构建程序，IDE 与引擎读同一份
**仓库：** `mcpp-community/mtest`；包的命名空间 `mcpplibs.mtest`
**上游：** [mcpp 2026-11-08-ecosystem-885-supplement-design.md](https://github.com/mcpp-community/mcpp/blob/main/.agents/docs/2026-11-08-ecosystem-885-supplement-design.md) S7（mcpp 的测试协议）

mtest 是一套测试系统：一份与语言、构建系统无关的规范，一个运行、调度、存储、分析与查询的引擎，一个 C++ 模块原生的测试库，以及与宿主构建系统的集成。mcpp 是它的第一宿主，也是集成最深的宿主。mtest 以 mcpp 与 C++ Modules 开发，以 openkal 为操作系统层，以 ok 映像发布，并以自身测试自身。

## 1. 动机

### 1.1 验证成为瓶颈

在 Agent 时代，编写代码的时间缩短，验证的时间没有缩短，瓶颈因此移到 CI、e2e、单元测试、一致性测试（CTS）与基准（bench）上。#885 收尾的记录给出了这一判断的依据：

| 现象 | 实例 |
|---|---|
| 长链路等待 | mcppls-clangd 一次对比运行约 2 小时；mcpp 发布前的 canary 约 50 分钟；mcppls 发布重跑整套 CI 约 1.5 小时 |
| 失败定位依赖人工 | 反复以 `gh api …/logs \| grep FAIL` 在数千行日志中寻找原因；CLion 无 JCEF 的失败经三轮才定位；Windows zlib 的配置经三轮 |
| 没有受影响测试的选择 | 改动一个脚本或一份配置即触发全量矩阵 |
| 基础设施失败与测试失败不分 | GitCode 下载停滞、索引未生效、macOS runner 被取消，均以整轮重跑处理 |
| 测量政策依赖人记 | darwin 的有效测量被重跑，违反 `ci/performance-policy.md` |
| 跨仓库状态依赖轮询 | 五个仓库的 PR 检查以手工轮询汇总 |
| 测试载体碎片化 | GoogleTest、三套自写的 C++ 测试工具（`mcppls.testing`、`mcpp.plugins.testing`、`mcppide.testsupport`）、bash e2e、python e2e 与对比运行、Kotlin IDE Starter、VS Code 扩展测试、nvim lua |

### 1.2 基线（初步）

GitHub 上最近成功的 PR 运行，以 `updatedAt − createdAt` 计（含排队与重跑，只作初步参考）：

| 项目 | 工作流 | 中位数 | 最大值 |
|---|---|---|---|
| mcpp | ci | 57 min（n=4） | 78 min |
| mcppls | CI | 52 min（n=40） | 505 min |
| mcpp-ide | CI | 21 min（n=31） | 65 min |
| mcpp-plugins | ci | 23 min（n=40） | 365 min |
| mcppls-clangd | build-test | 68 min（n=4） | 257 min |

最大值主要来自整轮重跑与排队，中位数主要来自全量矩阵与按系统分别构建。

## 2. 定位与原则

- **通用。** 规范与引擎与语言、构建系统无关；mcpp 是宿主之一，C++ 是语言之一。不依赖 mcpp 的项目以适配接入，得到其适配等级对应的能力。
- **规范优先。** mtest 的 C++ 库是规范的一种实现，在引擎中不享有特权；GoogleTest、doctest、Catch2 的适配与它处于同等地位。
- **对使用者零配置。** 在依赖中加入 mtest 即可用；`mcpp new` 默认选用它。
- **不强制适配。** 一个程序不实现协议时仍是一个以退出码判定的测试（L0）；不适配只意味着没有相应的能力，不产生错误，不要求迁移。
- **面向 Agent。** 输出结构化、简短、可复现；每一个失败回答三件事：在哪里、为什么、如何在本地复现。控制与数据以稳定的接口提供。
- **政策由工具执行。** 测量是否有效、能否重复、能否重试，由引擎依声明的政策判定。
- **自身是自身的用户。** mtest 的每一项能力先在 mtest 自身的测试中使用（第 9 节）。

### 2.1 按需使用

mtest 的每一部分可以单独使用，开发者按需要取其中几项，不必全部采用。各部分之间只共享数据模型（规范的 Schema），不互相要求：

| 只用 | 得到 | 不需要 |
|---|---|---|
| C++ 测试库（`mcpplibs.mtest`，或其中的 `bench`、`cts`、`e2e` 模块） | 无宏、无头文件的用例与期望；程序以退出码与报告通道工作 | 引擎、服务、mcpp 之外的任何东西 |
| 引擎的运行与报告（`mtest run`） | 对现有测试（GoogleTest、doctest、Catch2 或任何退出码程序）的并行运行、选择、只重跑失败的、报告 | mtest 的测试库 |
| 分析工具（`mtest analyze`、`hot`、`path`、`diff`） | 热点、耗时排名、关键路径、失败聚类 | 运行器：输入可以是 mtest 的存储，也可以是导入的 JUnit XML 或其他 CI 的结果 |
| 诊断（`mtest explain`、`trace`、`bisect`） | 失败包、深度追踪、二分定位 | 其余部分 |
| CI 汇总（`mtest ci`） | 跨仓库的检查状态与失败摘要 | 本地的运行与存储 |
| 服务（JSON-RPC / MCP） | Agent 的控制、订阅与查询 | 前端；服务只在需要时启动 |
| C ABI 报告库（`libmtest.okso`） | 其他语言的测试按协议报告 | C++ 库与引擎 |

- **分发上分开。** C++ 库是 mcpp-index 中的包（`mcpplibs.mtest` 与其模块），按依赖引入；引擎是 xim 中的工具（`mtest`），按需安装；C ABI 库随引擎发布；服务是引擎的一个子命令。只引入测试库的项目不下载引擎；只用分析工具的 CI 不构建任何 C++。
- **能力不捆绑。** 每个命令只读它需要的数据：分析不要求测试由 mtest 运行，诊断不要求存储中有历史（有则更好），CI 汇总不要求本地运行过测试。缺少的数据使输出相应地更少，而不是报错。
- **配置可省。** 默认值使最常见的用法无须配置；集合、政策、保留期、告警只在使用者声明时生效。

## 3. 架构

| 层 | 内容 | 实现 |
|---|---|---|
| 规范 | 对象模型、协议、结果与指标的数据模型、拓扑模型、适配等级；JSON Schema 带版本 | `spec/`，规范文本与 Schema |
| 引擎 | 运行、调度、存储、分析、查询、导出；CLI 与常驻服务 | C++ Modules，mcpp 构建，ok 映像发布 |
| C++ 库 | 用例、期望、夹具、参数化、属性测试、golden；`bench`、`cts`、`e2e` 模块 | C++ Modules，无宏、无头文件 |
| 适配 | GoogleTest、doctest、Catch2；脚本测试（bash、python 的薄垫片）；JUnit XML 导入（通用后备） | 各为一个包 |
| 其他语言 | 工具支持（引擎以协议运行任何语言的测试程序）与薄的 FFI 接口：一个以 C ABI 导出的报告库（`mtest_case_begin`、`mtest_case_end`、`mtest_expect_fail`、`mtest_metric` 等），各语言以其 FFI 绑定使用（Python ctypes、Rust、Go cgo、Kotlin/JNI、Lua FFI、Node N-API）；不提供其他语言的完整测试库 | C ABI 库由 C++ 实现，以 ok 映像库（`libmtest.okso`）加 C 头文件发布；原生程序经 openkal-bind 生成的绑定调用它（openkal-image docs/bind.md），一份产物服务全部系统 |
| 宿主集成 | mcpp：构建图、受影响选择、测试归档、`mcpp test`；其他宿主（CTest、cargo、go test、pytest、Gradle）经适配 | mcpp 侧为 S7 的协议与运行器 |
| 前端 | CLI；mcpp-ide 的用例树、时间线、关键路径与热点视图；web UI | 共用数据模型与拓扑 |

### 3.1 openkal 原生

- **引擎以 ok 映像发布。** 一份 `mtest.okb` 经 okrun 在 Linux、macOS、Windows 上运行，与 mcppls、mcpp-ide 后端的发布形态一致（补充方案 S1）。引擎经由 mcpplibs.os 使用操作系统：进程（`process::run` 的有界运行与单元）、文件、目录、终端、网络（CI 汇总）、IPC（常驻服务）。不包含任何系统头文件，不含预处理平台分支（补充方案 S4）。
- **运行平台的判断在运行时。** 引擎中凡需随系统变化的行为（路径约定、可执行文件后缀、子进程的组织）经 `os::host()`、`os::conventions()` 与补充方案 S2 的两层判断取得。
- **被测程序可以是映像。** 测试程序以 `<arch>-openkal` 构建时，引擎以 okrun 运行它们；一次构建产生的测试归档在四个系统上运行（mcpp SPEC-015）。被测程序也可以是原生的，引擎同样运行。
- **C++ 库同时支持原生与映像。** 库只依赖 `std` 与 mcpplibs.os，因而随使用者选择的目标编译：原生构建、ok 映像、交叉目标皆可。

### 3.2 对 openkal 体系的专门支持

openkal 的实现之间只要符合规范即可互换：一个映像在任一系统的 okrun 上运行，一个 C 库或 C++ 运行时在任一实现之上工作。mtest 把"符合规范"变成可检验的事实，并把底层的变动置于严格的门禁之下。

- **规范一致性套件（cts）。** openkal SPEC 的每一条款对应一组用例（条款标识即 SPEC 的编号，如"clause 30"），由 mtest 的 cts 模块编写；同一套件对 openkal 的每个实现运行：openkal-linux、openkal-macos、openkal-windows、openkal-emscripten，以及映像经 okrun。结果是条款 × 实现 × 系统的矩阵，未覆盖与预期失败的条款带到期日列出。
- **跨实现与跨版本的互通。** 映像以一个版本的平台构建，在其他版本的 okrun 上运行（向后兼容的范围由规范声明）；C 库、C++ 运行时与实现的版本组合按平台版本组（D12）测试。结果记录在存储中，作为平台版本组的发布依据。
- **接口面的变化检测。** okrun 绑定的名字（`okrun_names()`）、各实现导出的 `kal_*` 与可选接口位（`KAL_IFACE_*`）在每次运行时记录；与上一个发布比较，新增、删除与签名变化逐项报告，删除与不兼容的变化使门禁失败。
- **映像为一等对象。** 引擎认识 okrun 这一运行器：测试一次构建为映像，测试归档在三个系统上运行；okrun 的测量（`OKRUN_PROF`）与调试接口是深度追踪的映像一侧（6.3）。
- **底层变动的门禁。** 对标为基础设施的包（openkal 家族、openkal-platform、mcpplibs.os、mwrap 包装、okrun 与 okld），`release` 集合除 4.5 的内容外还要求：
  - 规范一致性套件在每个实现与系统上无新增失败，覆盖不下降；
  - 接口面无未声明的删除或不兼容变化，新增的接口在规范中有对应条款；
  - 下游的固定使用者（mcpp、mcppls、mcpp-ide 的映像测试）以候选版本通过（与 mcpp 的发布 canary 同一做法）；
  - 性能 bench 无回归（政策判定）；
  - 一份审查记录：变动对应的规范条款、兼容性结论与审查者，随发布保存。

  门禁由引擎执行，记录进入存储，发布流程读取门禁的判定而不是人工的确认。

### 3.3 以 mcpp 与 C++ Modules 开发

- 仓库是一个 mcpp 工作区：`spec`（Schema 与生成的数据类型，生成由 `build.mcpp` 完成，不提交生成文件）、`core`（数据模型与协议）、`lib`（C++ 测试库）、`engine`（运行与调度）、`store`（存储与查询）、`analysis`（指标与拓扑）、`cli`、`service`（JSON-RPC）、`adapters/*`。
- 每个成员只导出模块，接口单元与实现单元分开，层次单向依赖并由检查保持（与 mcppls `devtools check layers` 相同的做法）。
- 依赖为精确版本、身份键、一张表（补充方案 S5）。

## 4. 规范

### 4.1 对象模型

套件（suite）→ 程序（program）→ 用例（case）。每个对象带稳定标识（跨运行不变，由来源路径与声明名派生）、类别（`unit`、`e2e`、`cts`、`bench`）、标签与属性。资源（resource）与产物（artifact）是一等对象：用例声明它需要的资源（串行组、独占机器、GPU、网络）与它依赖的产物（构建目标、数据文件）。

### 4.2 协议

测试程序与引擎之间：

- **能力声明：** 程序声明它实现的协议版本与等级；在 mcpp 中由提供测试入口的包以 `kind = "entry"` 声明（docs/08 的 `[test] main`）。
- **列出：** 引擎以协议参数启动程序，程序输出用例清单（标识、显示名、源位置、类别、标签、资源、预期）。
- **选择：** 以用例标识选择；转义与通配由协议规定。
- **报告：** 程序把事件写到引擎给出的通道（NDJSON）：用例开始、结束、状态（通过、失败、跳过、预期失败、无效测量）、耗时、失败位置与消息、期望的结构化差异、输出、产物、指标。
- **上下文：** 引擎为单个用例给出环境、工作目录与临时目录；用例在同一进程或各自进程中运行由引擎决定，程序声明它支持哪种。

### 4.3 适配等级

| 等级 | 程序要做的 | 得到的能力 |
|---|---|---|
| L0 | 无 | 程序级的运行、耗时、归档、历史 |
| L1 | 列出、选择、报告 | 用例树、单个用例的运行与复现、失败位置与差异 |
| L2 | 报告指标 | bench 的统计、基线比较、政策判定；CTS 的条款覆盖 |
| L3 | 声明资源与产物依赖 | 受影响测试的选择、按资源调度、关键路径 |

mtest 的 C++ 库实现 L3；GoogleTest 等适配实现 L1；脚本垫片实现 L1，可声明 L3 的依赖。

### 4.4 类别

- **unit：** 状态、失败位置、差异、输出。默认并行。
- **e2e：** 依赖的产物（构建目标、外部工具）、环境、产物索引（日志、截图、报告）。
- **cts：** 用例标注其覆盖的规范条款（条款标识在项目的追踪表中声明，如 mcppls 的 `conformance/traceability.json`）；预期失败清单（已知缺口）带到期日；按平台的结果矩阵。
- **bench：** 样本、配对与交替（消除机器漂移）、中位数与离散度、基线；判定分为通过、未达限、无效测量三种。政策（配对数、离散界、上限、能否重复）在项目中声明，引擎执行：有效而未达限的测量不得重复（`ci/performance-policy.md` 的规则成为通用能力）。

### 4.5 测试集合：smoke、回归与门禁

类别（4.4）回答"测的是什么"，集合回答"何时跑、跑到哪里为止"。集合是命名的选择，在项目中声明，引擎执行：

| 集合 | 内容 | 典型用处 |
|---|---|---|
| `smoke` | 每个功能面一到数个最快的用例，带总时间上限（声明，例如 60 s，引擎在超出时报告） | 每次提交的第一道门；发布后的安装验证（干净环境中运行已安装的产物，即 #885 的 xlings 全生态验证）；`mcpp new` 生成的项目 |
| `regression` | 标注了所防止缺陷的用例（`regression = "mcpp#903"`），及历史上失败过的用例 | PR 门禁；修复的验收（关闭 issue 时引用其回归用例与运行） |
| `pr` | 受影响选择后的用例，加 `smoke` 与受影响范围内的 `regression` | PR CI |
| `full` | 全部用例 | main CI、夜间运行 |
| `release` | `full` 加 bench 的政策判定与 cts 的条款覆盖 | 发布门禁 |

- **声明。** 集合由标签、类别、路径与条件组合定义，并可继承（`pr` 含 `smoke`）；用例可属于多个集合。集合的定义写在宿主清单（mcpp 的 `[test.sets]`）或项目的 mtest 配置中。
- **回归的来源。** 用例以属性标注它所防止的缺陷；引擎在存储中记录每个用例的失败历史，最近失败过的用例自动进入 `regression`，保留期可声明。关闭一个缺陷时，`mtest explain --regression mcpp#903` 给出覆盖它的用例与最近一次通过的运行。
- **定位回归。** `mtest bisect <case> <good>..<bad>` 在两次提交之间二分，每一步只构建与运行该用例（受影响选择与测试归档使每一步的代价是一个用例），给出首个失败的提交。
- **smoke 的上限。** smoke 有时间预算；超出预算的用例被报告，提示移出 smoke，避免第一道门变慢。
- **安装后的 smoke。** smoke 可对已安装的产物运行（不构建，只运行），用于发布后的验证与用户环境的诊断（`mtest smoke --installed`）。

### 4.6 粒度

属性在包、套件、程序、用例四级声明，后一级覆盖前一级：包级在宿主清单（mcpp 的 `[test]`）中，其余在代码中或由构建插件声明。可声明的属性：标签、超时、资源、隔离方式、环境与工作目录、重试政策（只对标为不稳定的用例生效）、预期失败与跳过条件（平台、目标、能力）、bench 的样本数与政策。选择可按标识、标签、类别、集合（4.5）、受影响集合与时间预算组合。

## 5. 引擎

- **运行与调度：** 按资源锁并行；以历史耗时最长者先行；按历史均衡分片（CI 多机）；时间预算内的选择；PR 上的快速失败；只重跑失败的用例；基础设施失败（下载停滞、runner 取消、宿主不可用）单独分类，不计为测试失败，按政策只重跑受影响的用例。
- **存储：** 每次运行一条记录（运行标识、宿主、机器、提交、选择、结果、指标、拓扑快照）；本地存储与 CI 产物同一格式，CI 产物可以回收入库；保留期在配置中声明。
- **分析：** 第 7 节的指标；回归告警；不稳定用例的识别、隔离名单与到期。
- **CI 汇总：** 跨仓库收集一组 PR 的检查状态与 mtest 结果，给出失败摘要。

## 6. 配套工具与服务，及其 Agent 接口

mtest 不止是开发者写测试的接口：围绕测试结果的数据、分析工具与常见服务是它的组成部分，而且每一项都以同一套接口同时服务人、CI 与 Agent。原则是"一项能力，三个入口"：CLI（`--json`）、常驻服务（JSON-RPC，可封装为 MCP 工具）、数据文件（带 Schema 的 NDJSON 与图），三者给出同一份数据。

### 6.1 服务与工具

| 类别 | 能力 | 命令 / 服务方法 |
|---|---|---|
| 运行 | 运行、按集合与受影响范围选择、预算内选择、只重跑失败的、watch | `mtest run`、`mtest plan`、`mtest rerun --failed`、`mtest watch` |
| 状态 | 正在进行的运行、每个用例的状态、进度与预计剩余时间、资源占用 | `mtest status`；服务事件 `run/progress`、`case/started`、`case/finished` |
| 控制 | 开始、取消、重跑单个用例、隔离或解除隔离不稳定用例、更新 golden | `mtest cancel`、`mtest quarantine`、`mtest golden --update`；服务方法同名 |
| 结果 | 单次运行的报告（人读的摘要、JUnit XML、静态 HTML 报告作为 CI 产物）、两次运行的差异 | `mtest report`、`mtest diff <run> <run>` |
| 诊断 | 失败的原因、位置、期望差异、复现命令、相关改动；关闭缺陷时的回归证据；二分定位 | `mtest explain`、`mtest explain --regression <issue>`、`mtest bisect` |
| 历史与查询 | 声明式查询存储；用例、程序、套件的时间序列 | `mtest query`、`mtest history <case>` |
| 分析 | 第 7 节的指标：热点、耗时排名、构建与运行占比、关键路径、并行效率、不稳定率、失败聚类、成本（runner 分钟） | `mtest analyze <指标>`、`mtest hot`、`mtest path` |
| 拓扑 | 关系图导出与受影响集合 | `mtest graph --format json|dot|mermaid`、`mtest affected <改动>` |
| CI 集成 | 跨仓库汇总多个 PR 的检查与 mtest 结果；把失败写成检查注解与 PR 摘要；回收 CI 产物入库 | `mtest ci status <prs…>`、`mtest ci annotate`、`mtest ci collect` |
| 门禁与告警 | 集合的门禁判定、指标回归告警（例如 smoke 超出预算、bench 未达限、不稳定率上升） | `mtest gate <集合>`、`mtest watch-metrics` |
| 维护 | 存储的保留与压缩、隔离名单的到期、结果库的校验 | `mtest store gc`、`mtest store verify` |

### 6.2 Agent 的控制、信息与分析

- **控制：** 每个操作以运行标识为单位，幂等，返回分类固定的结果；Agent 可以启动运行后断开，以运行标识再次查询状态或取消。
- **信息与状态：** 服务提供订阅：运行的进度、用例的开始与结束、门禁的判定，作为事件流（与 mcpp-ide 的 job 事件同一模型）；轮询的 `mtest status --json` 给出同一份状态。
- **分析：** 分析命令返回结构化结果（指标、单位、区间、样本数、数据来源的运行标识），附简短的结论字段（例如"耗时上升 23%，自运行 X 起，集中在 3 个用例"），使 Agent 不必自行计算即可行动。
- **工具目录：** 服务以带 JSON Schema 的工具目录描述全部方法（名称、参数、返回、效果），可直接作为 MCP 工具注册；目录随版本演进，旧方法以兼容期保留。
- **约束与安全：** 运行可声明效果约束（是否联网、可写目录），沿用 mcpp effects 的模型；Agent 可在受限模式下运行；访问 CI 的令牌只来自环境或系统凭据，不进入存储与输出。
- **简洁：** 默认输出只含摘要与失败；细节按需展开，长输出以产物引用代替内联，Agent 读取的上下文因此保持小。
- **工作流文档：** 常见任务（PR 失败的诊断、修复的验收、性能回归的定位、发布门禁）各有一页以命令序列描述的流程，供人与 Agent 照做。

### 6.3 失败信息的捕获与深度追踪

**失败时自动捕获。** 用例失败（或超时、被信号终止）时，引擎为该用例收集一份失败包，按运行标识存入存储，`mtest explain` 与 `mtest artifacts <case>` 读取它：
- 期望的结构化差异、断言位置与调用栈（经符号化；原生程序用系统的符号化器，映像经 okrun 的符号表与 GDB JIT 接口）；
- 标准输出与标准错误（有界，超出部分以产物引用）、用例的环境与工作目录、启动方式（mcpp 的 `--print-launch` 记录）；
- 程序被信号终止时的核心转储或 Windows 的 minidump（受大小上限与保留期约束；不可得时说明原因）；
- 用例声明的产物（日志、截图、生成的文件）；
- 同一用例最近几次运行的结果，用于区分新失败、反复失败与不稳定。

**按需的深度追踪。** 使用者对某个用例或场景运行带工具的复现，`mtest trace <case> --with <工具>`：只构建与运行该用例，结果进入同一存储并与基线对照。

| 工具类别 | 工具 | 获得的信息 |
|---|---|---|
| 内存与未定义行为 | ASan、UBSan、TSan、MSan；Valgrind | 越界、释放后使用、数据竞争、未初始化读取，带调用栈 |
| 性能 | Linux perf、macOS 的采样（`sample`/Instruments 的命令行）、Windows ETW；映像经 okrun 的测量（`OKRUN_PROF`：调用计数与耗时、程序登记的计数器、perf map） | 热点函数、火焰图、调用耗时 |
| 资源 | 峰值内存、页错误、文件与进程数、墙钟与 CPU 时间 | 资源随版本的变化 |
| 系统调用 | strace、ltrace、dtruss | 程序与系统的交互 |
| 记录与重放 | rr（Linux） | 失败的确定性重放，供调试器逐步回溯 |
| 调试器 | gdb、lldb、Visual Studio 调试器，经启动描述附加 | 交互式定位 |

- **编排而不实现。** mtest 不实现这些工具，而是编排它们：消毒器经构建配置引入（mcpp 的 profile，例如 `[profile.asan]`，由宿主适配选择），运行包装器经宿主的 `run_under` 前缀引入，报告由工具适配解析为结构化结果（位置、调用栈、分类）。新增一种工具是一个适配，不改引擎。
- **映像与原生。** 消毒器与多数系统工具作用于原生构建，因此深度追踪在原生构建目标上进行（补充方案 S1 的"构建目标"角色）；映像的追踪使用 okrun 自带的测量与调试接口。
- **结果的比较。** 追踪结果按用例与运行标识存储，`mtest diff` 与 `mtest analyze` 在两次追踪之间比较热点与资源，回归告警（6.1）可以基于追踪指标。
- **Agent 使用。** 追踪与失败包经同一接口提供：Agent 对失败用例调用 `mtest explain`，需要时调用 `mtest trace --with asan`，读取结构化的发现，不必解析工具的原始输出。

## 7. 拓扑与分析

- **拓扑：** 源文件 → 构建目标 → 测试程序 → 用例 → 资源与产物 → 运行实例。以稳定的 JSON 图格式导出，并可导出 DOT 与 Mermaid。图上计算关键路径、受影响集合、并行度与资源争用；插件与 UI 工具读这份图做可视化。
- **指标规范：** 耗时分布（按用例、程序、套件、类别）、构建与运行的占比、关键路径长度、并行效率（总 CPU 时间 / 墙钟 × 并行度）、排队时间、缓存命中率、不稳定率、失败聚类（按消息与位置）、重跑次数、从失败到定位的时间、runner 分钟成本。每个指标有定义、单位、来源、保留期与回归告警的阈值。
- **前端：** mcpp-ide 的用例树、时间线、关键路径图与热点图读同一份数据与拓扑；web UI 与 CI 的静态 HTML 报告以后复用同一前端组件。

## 8. 面向开发者的能力

- watch 模式；只重跑失败的；聚焦与跳过；默认并行。
- 期望失败时给出结构化差异；golden 与快照测试，带更新开关；参数化与属性测试；自动清理的临时目录夹具。
- 测试代码无宏、无头文件：位置由 `std::source_location` 记录，用例以函数或用户定义字面量注册，期望以普通函数表达。
- 人读的输出简短，失败处给出复现命令。

## 9. 自身是自身的用户

- mtest 的全部测试以 mtest 编写与运行：C++ 库的单元测试、引擎的 e2e（以真实的测试程序为夹具）、协议的一致性测试（CTS，条款对应规范文本）、引擎自身的 bench（调度、存储与查询的耗时）。
- mtest 的 CI 以 mtest 运行：受影响选择、分片、只重跑失败的、失败摘要；其 CI 时间是第 10 节指标的第一组数据。
- 引擎的测试以 ok 映像在四个系统上运行，与发布物一致。

## 12. 多视角自我审查

| 视角 | 审查所见 | 处理 |
|---|---|---|
| 架构 | 引擎既服务 mcpp 又宣称通用，可能被 mcpp 的需求带偏 | 规范与引擎不引用 mcpp 的任何概念；mcpp 的集成是宿主适配，与 CTest、cargo 的适配同一接口 |
| 架构 | 引擎以 ok 映像运行，而它要启动被测程序（原生或映像）并管理其单元 | os 的 `process` 在映像中提供进程、单元与有界运行（mcppls、mcpp-ide 已在用）；启动被测映像经 okrun，路径由 mcpp 给出 |
| 稳定性 | 调度与选择依赖历史数据，数据缺失或陈旧时会误选 | 没有历史时退回全量；受影响选择只依拓扑，不依历史；`mtest plan` 输出理由 |
| 稳定性 | 只重跑失败的用例，可能掩盖顺序依赖 | 重跑在新进程中单独运行该用例；结果与首次不同则标为不稳定并计入指标 |
| 一致性 | 生态已有三套自写测试工具，迁移期间并存 | 各项目在其版本 PR 中整体迁移，不保留双套；迁移完成即删除旧工具 |
| 兼容性 | 现有测试不能因 mtest 而失效 | L0 不要求任何改动；`mcpp test` 的现有行为与输出保持 |
| 跨平台 | Windows 的进程启动开销与 Unix 不同，每用例一进程的隔离在 Windows 上较贵 | 隔离方式由引擎按用例的声明与平台选择；同进程运行为默认，需要隔离的用例声明之 |
| 性能 | 结果存储随时间增长 | 保留期与压缩在配置中声明；查询按运行与时间分区 |
| 用户体验 | 功能多，默认体验可能变重 | 默认只有运行与摘要；分析、汇总与可视化按需调用；各部分可单独使用与单独分发（2.1） |
| Agent 可操作性 | 自由文本输出难以被 Agent 可靠使用 | 所有输出有 Schema 与版本；退出码分类固定；失败摘要有固定字段；分析结果带结论字段 |
| Agent 可操作性 | 能力分散在多个入口时，Agent 只能用到其中一部分 | "一项能力，三个入口"：CLI、服务（工具目录可注册为 MCP）、数据文件给出同一份数据（6.1） |
| 架构 | 服务化的功能（CI 汇总、告警、HTML 报告）可能把引擎变成一个需要部署的系统 | 全部能力以本地 CLI 与可选的本地常驻服务提供，不需要服务器；CI 中以命令运行，结果作为产物 |
| 安全 | CI 汇总需要访问令牌；Agent 以受限模式运行 | 令牌只来自环境或系统凭据，不写入存储；效果约束由引擎执行 |
| 测试覆盖 | 引擎自身的正确性决定所有项目的判定 | 第 9 节：mtest 以自身测试自身，协议有 CTS，引擎在四个系统上以映像测试 |
| 目标 | "减半"若无正式基线则不可检验 | 迁移前测量正式基线；指标定义写入规范 |
| 用户体验 | smoke 随时间变慢、regression 集合无限增长，第一道门失去意义 | smoke 有时间预算并报告超出者；regression 中由失败历史加入的用例有保留期，由缺陷标注加入的用例常驻 |
| 测试覆盖 | 修复关闭时没有证据说明它被测试覆盖 | 回归用例以属性标注缺陷，关闭 issue 时引用其用例与通过的运行 |
| 稳定性 | 失败包与核心转储可能很大，长期保存会挤占磁盘 | 转储与产物有大小上限与保留期，按运行分区，`mtest store gc` 回收；上限可声明 |
| 架构 | 每种追踪工具的输出格式各异，引擎若逐一内建会无限膨胀 | 工具以适配接入（构建配置、运行包装器、报告解析），引擎只编排与存储结构化结果 |
| 稳定性 | 底层库（openkal、os、平台）的变动影响全部映像与使用者，人工审查容易遗漏接口或兼容性变化 | 规范一致性套件、接口面变化检测、下游 canary 与审查记录作为基础设施包的发布门禁（3.2） |
| 一致性 | openkal 的实现之间"符合规范即可互换"若无检验，只是一句陈述 | 条款 × 实现 × 系统的一致性矩阵与跨版本互通测试（3.2） |
| 范围 | 项目范围大，容易在设计中扩散 | 规范、引擎、C++ 库、mcpp 集成与首批迁移在一份设计中完整给出；适配等级描述能力，不作为分期 |

## 14. 用例的运行场所与机器能力（0.8.0）

**问题。** 0.7.0 的 `[capabilities]` 只由引擎在选择时求值。实现协议的其他运行器（`mcpp test`）与单独运行的程序不求值，使用方因而在用例上同时写标签 `requires:<词>`、在用例体内再次判断，并另维护一份探测表；用例必须通过的平台另写在 `[ci.coverage] hosts` 的表中，与用例分离。

**决定。**

1. **场所。** `only{...}` 与 `except{...}` 以 mcpplibs.os 的平台与架构陈述用例在何处运行：`only` 的平台之间、架构之间为"或"，二者之间为"与"；套件与用例的 `only` 取交集，`except` 累加。场所之外，用例跳过，原因为 `only on <场所> (this host: <系统> <架构>)` 或 `not on <场所> (...)`。库、Bash 与 Python 适配器由程序自行判定；引擎依据清单中的 `only`、`except` 同样判定，以覆盖只列出场所的实现（C ABI）。
2. **编译期选择。** 不新增宏或常量：mtest 重新导出 mcpplibs.os 的 `platform`、`architecture`、`can_run_on`、`host`、`on<P>`。`on<P>([&](auto){...})` 的函数体在不能运行于 `P` 的构建中被丢弃，承担 `if constexpr` 的作用；openkal 镜像在加载时得知 `host()`，与第 3.1 节一致。
3. **能力。** `capability` 以 `[capabilities]` 的同一组检验（系统、架构、PATH 上的程序、glob、命令、环境变量、`all`/`none`）加一个函数在代码中声明一次，由程序在每个进程中求值一次，并作为属性使用（`"x"_test[gcc]`，同时带标签 `requires:gcc`）。缺失时用例跳过，原因与引擎相同：`missing capability: <名> (<未成立的检验>)`。在模块接口中声明的能力先于导入它的单元初始化，因此命名空间作用域的套件可以使用。
4. **协议。** `case` 事件新增可选字段 `only`、`except`、`capabilities`（名到布尔）与 `reason`（`expect` 为 `skip` 时的原因）。引擎对程序已回答的能力词不再要求 `[capabilities]` 声明，并把答案记入运行记录；`[capabilities]` 继续服务于脚本程序。
5. **覆盖。** `mtest ci coverage` 要求陈述了 `only` 的用例在所收集运行覆盖到的每个场所上通过，且至少有一个运行位于其场所；场所由用例自身陈述，不再需要表格。

**兼容。** 新字段均为可选；未陈述场所与能力的程序、清单与配置的含义不变。
